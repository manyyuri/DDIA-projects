# INTERVIEW — singleleader 讲解

## 30 秒定位

> "单主复制的教学实现，但问题不是'怎么复制'，而是**'什么才算写成功'**。我做了 Async / Quorum / WaitForAll 三种 ack 模式，每种都用故障注入测出了它的失败模式：Async 会丢掉已经 ack 给客户端的写；quorum 拿掉了就是丢数据；超时返回失败的写其实可能已经提交。这三条全有专门的测试复现。"

## 两分钟讲解稿

> "写流程：客户端写 leader，leader 追加日志后**什么时候回复**，就是这个模块的全部戏剧性。Async 是 leader 本地落了就 ack——延迟最低，但 failover 时没复制出去的写全部蒸发，而且是**已经告诉客户端成功的写**，RPO 大于零。Quorum 是多数派持有才 ack，容忍少数派故障，延迟取决于中位数副本。WaitForAll 是配置里**所有**副本都持有——注意是配置里的全部、不是活着的全部，这才是'到处都持久'，代价是任何一个副本宕机整个系统不可写。
>
> 三个用测试钉死的认识。第一，**ack 不等于 commit**：提交还需要'多数派持有 且 这一条属于当前 term'——这是 Raft 的提交规则，我照搬了。第二，**commit 也不等于永远在**：`TestLosingTheQuorumLosesCommittedWrites` 用 5 节点，n4/n5 被隔离、写只落在 n1/n2/n3，然后把这仨全杀——新 leader 上台，3 条已提交的写没了。**持久性是副本集合的属性，不是某个节点上的布尔值**。第三，**超时不等于失败**：WaitForAll 遇到副本宕机超时报错，但那条写可能已经在 quorum 上提交了——客户端重试就会产生重复写。这就是幂等键存在的物理理由。
>
> 读这边我也做了三种模式：走 leader、读 follower（便宜但可能陈旧）、带会话水位的读己之写。关键是认识到**'读己之写'是客户端会话的属性**——服务器根本不知道'这个客户端上次写到哪'，必须客户端自己把上次写的位置带上，副本落后就拒绝回答。"

## 可主动抛出的数字 / 断言

- 三种模式的失败面各有一个测试：`TestAsyncAckIsLostOnFailover` / `TestLosingTheQuorumLosesCommittedWrites` / `TestTimedOutWriteMayStillHaveCommitted`
- Async：failover 丢的写 = ack 时还没复制出去的窗口
- WaitForAll：任一副本宕 → 不可写（可用性换持久性）

## 追问链

**Q1：异步复制会丢数据，为什么生产上 MySQL/Kafka 还大量在用？**
> "因为这是一个显式的 RPO 换延迟的交易。MySQL 异步复制、Kafka acks=1 都是这个选择：正常路径少等一轮跨网络 RTT。要紧的是把 RPO 量化——异步模式下丢失窗口 = 'leader 落盘到 follower 拉走'之间那段时间，加上 failover 决策时间。业务能接受多少毫秒的数据丢失，决定选哪种模式。MySQL 的半同步（至少一个 follower 确认）就是在两端之间调旋钮。"

**Q2（追）：那 Kafka 的 acks=all 呢？**
> "acks=all 对应我的 WaitForQuorum——ISR 里所有副本确认。但注意 Kafka 的 ISR 是动态收缩的：ISR 只剩 leader 自己时 acks=all 退化成 acks=1。所以 Kafka 还有 min.insync.replicas=2 兜底——ISR 不足就宁可拒绝写。这正是我 WaitForAll 和 Quorum 之间的那条缝：**'配置里的全部'和'活着的全部'是两个不同的承诺**。"

**Q3：为什么提升新 leader 前要先追加一条自己 term 的 no-op？**
> "因为提交规则要求'多数派持有 且 属于当前 term'。新 leader 的日志里可能有前任的条目，但它不敢直接宣布这些旧 term 条目已提交——Raft 论文 Figure 8 的反例：旧 term 条目即使多数派持有，也可能被覆盖。先提交一条自己 term 的 no-op，它提交时前面的条目随之提交，相当于一道屏障。我在 raft 模块实际踩过这个坑：failover 测试报 `k9 vanished`，新 leader 日志里有数据但读不到，加 no-op 屏障才修好。"

**Q4：超时之后客户端到底应该重试还是报错？**
> "都不能盲做。超时只意味着'不知道结果'：写可能已提交。正确姿势是带**幂等键**重试——服务端按请求 ID 去重，重试要么返回上次的结果、要么继续等待，绝不产生第二条副作用。没有幂等键的重试是重复写事故的标配。我的 minidb 里客户端就是循环重试 + 等待提交，而不是报错放弃。"

**Q5（追）：如果两个客户端超时都重试了呢？**
> "幂等键是按客户端请求维度的：每个客户端一个唯一 ID，服务端记住'这个 ID 对应的结果'，第二个客户端的 ID 不同、走正常冲突路径。幂等解决的是'同一请求的重复'，不是'不同请求的并发'——后者靠并发控制（mvcc 模块的 CAS/隔离级别）。"

**Q6：读己之写为什么不能靠'读写都走 leader'解决？**
> "能，但那是用可用性和扩展性换的：leader 单点、不能水平扩展读。会话水位是更便宜的方案——客户端记住上次写的位置（例如全局 index），发给任何副本，副本的 apply 位没追到这个位置就拒绝或等待。代价是它只保证**这个会话内**的读己之写和单调读；换个会话（另一台机器）就没了。Monotonic reads、consistent prefix read 这些一致性级别，都是在这个谱系上按会话 negotiated 的。"

**Q7：你这个没有选举，Promote 是手工的，那 failover 是怎么做的？**
> "故意的。很多真实部署就是外部脚本/ Orchestrator 提升从库——这正是它们丢数据的原因。我的 Promote 按'活着的里面日志最长'选，但**不比较 term**，这是无共识系统里能做的最好猜测：日志最长的副本可能恰好缺一条已被旧 leader ack 的写。FailoverReport 会把丢了多少条写报出来，这个数字就是'没有共识的代价'的可视化。"

## 对照真实系统

- MySQL 主从 + 半同步：Async→WaitForOne 的连续谱；GTID 解决重试幂等；
- Kafka acks=0/1/all + min.insync.replicas：恰好是三种模式 + ISR 收缩保护；
- MongoDB writeConcern majority / w:1 / w:N：同样的旋钮，甚至名字都像。

主动说："这三个系统暴露给用户的其实是同一个 API——写成功到什么程度算成功。我把这个 API 的每个档位都做了一次故障实验。"

## 主动承认的边界

- 无选举协议（外部 Promote，不比较日志 term——这正是不安全的根源，也是教学点）；
- 无快照，日志无限增长；
- 复制是逐条推送，无流水线/批量。

一句话收尾："这个模块让我真正记住一句话：**复制不是备份，ack 不是承诺，超时不是失败**——三条都有测试编号。"
