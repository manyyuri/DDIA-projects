# INTERVIEW — eventsourcing 讲解

## 30 秒定位

> "事件溯源 + CQRS：不存当前状态，存事实序列。四个机制最值得讲：**版本号 CAS 就是乐观并发控制**（一次 CAS 防住丢失更新和写偏斜两类问题）；命令是纯函数所以重试天生安全；读模型（投影）可随时删掉重建；快照只是优化——我把快照删光，余额和版本分毫不差，有测试证明。"

## 两分钟讲解稿

> "写入流程：命令进来 → 加载聚合（重放该流的历史事件）→ 在内存状态上校验不变量 → 产出新事件 → **带着 expectedVersion 做 Append**。如果流的当前版本和预期不一致就是 ErrVersionConflict——这本质是**对整个聚合的一次 compare-and-swap**。
>
> 这个 CAS 同时干掉了两类经典问题。丢失更新：两个事务都从版本 2 读到余额 100、各自想取 80，第一个 append 成功，第二个拿到版本冲突，**重新加载**后发现余额只剩 20，被业务规则拒绝——注意是重载后重新决策，不是盲目重放。写偏斜：mvcc 模块里写偏斜靠'写集不相交'溜过冲突检测，而这里**任何写都要过同一个版本闸门**，聚合内不存在'不相交'——粒度换来了正确性。
>
> 因为命令是纯函数（完全由已加载状态决定、无副作用），重试永远安全。副作用（发短信、调支付）必须挪到事件订阅侧——这是事件溯源的纪律，不是偏好。
>
> 读模型是投影 tail 全局日志建出来的，**可丢弃**：我把 balances 改成错误值，Rebuild 从位置 0 重放就恢复了——投影 bug 修完重建、新查询维度新起一个投影追，运维上非常自由。代价是最终一致。
>
> 快照只是优化：LoadAccountFast = 快照 + 快照之后的事件增量重放。我的测试断言三者的余额和版本完全相同——全量重放、快照增量、没有快照。**这条断言就是整个模块的灵魂：事件是真相，快照是缓存**。如果哪天快照和重放对不上，那是 bug，不是取舍。"

## 可主动抛出的数字 / 断言

- `TestConcurrentCommandsCannotDoubleSpend`：并发取款，第二个 ErrVersionConflict → 重载 → 被余额规则拒
- `TestProjectionCanBeRebuiltFromScratch`：读模型故意写坏 → Rebuild 精确恢复
- `TestSnapshotPlusReplayEqualsFullReplay`：三种加载方式（全量/快照增量/无快照）结果全等

## 追问链

**Q1：版本 CAS 为什么能防写偏斜，行级冲突检测为什么不能？**
> "写偏斜的成因：两个事务读集重叠、**写集不相交**，行级写冲突检测看不见对方的写。版本 CAS 的粒度是**整个聚合**——'医生值班'例子里，如果排班是同一个聚合，两个'我要下线'命令都要过同一个流的版本闸门，第二个必然冲突。代价是把并发控制粒度从行放大到聚合：高并发改同一聚合时吞吐下降（重试增多）。所以聚合边界的划分直接决定并发性能——这是事件溯源设计里最难也最关键的决策。"

**Q2（追）：如果两个医生是不同聚合呢？**
> "那写偏斜回来了——CAS 只在聚合内有效。跨聚合一致性事件溯源本身不给，要么 saga/流程管理器编排，要么把'值班表'建成为独立聚合（第三个聚合管总量），要么接受最终一致+业务补偿。这个回答的要点是：**我知道 CAS 的保护半径**，它不是魔法，是'把并发收敛到单点串行'的机制，半径之外的问题它不管。"

**Q3：命令为什么必须是纯函数？**
> "因为冲突重试的核心动作是'重新加载、重新执行命令'。如果命令执行中有副作用——发了一条短信——重试就发两条。纯函数保证同样的输入状态得到同样的决策，副作用全部推迟到'事件已确认提交'之后的订阅侧，那里天然 at-least-once，用幂等消化。这条纪律在工程上挡掉一整类'重试重复扣款'事故。"

**Q4：快照和事件重放会不会不一致？**
> "会出问题的场景：快照的版本号和事件流版本错位（快照说 v5，但 v3、v4 事件被'优化'删了）。我的 LoadAccountFast 有个 `e.Version > a.Version` 的过滤：快照之后到达的事件才应用——快照存的是'已折叠到 v5 的状态'，重放只补增量。TestSnapshotPlusReplayEqualsFullReplay 三方对账就是防退化的。运维上：快照永远可以从事件重建，坏了就删掉重拍——**快照没有理由成为真相，因为真相在事件里**。"

**Q5：投影游标为什么用 GlobalPos 不用 Version？**
> "Version 是流内序号，acct-A 的 v7 和 acct-B 的 v7 毫无关系。投影 tail 的是全局日志，游标必须是全局单调的 GlobalPos。混用会造成漏事件（把 A 的 v7 当成'全局处理到 7'，B 的 v3 事件被跳过）。这是我显式设计的双序号结构：**Version 管流内并发（CAS），GlobalPos 管全局顺序（游标）**——两个问题两套序号，别混。"

**Q6：事件 schema 要改字段，怎么办？**
> "铁律：**历史事件永不原地修改**——它们是不可变的事实，也是审计的全部依据。正确姿势：① 加新字段（默认值），老事件读出来是零值——向前兼容；② upcasting：读取老版本事件时套一层适配器升级成新形状，投影逻辑只面对最新 schema；③ 双写过渡期 + 验证后下线旧字段。麻烦但可控；反过来原地改历史事件，等于伪造历史，审计和重建全部失真。我的实现没做 upcasting（列在边界），但我知道它是生产事件溯源最重的一块。"

**Q7：投影挂了三天，恢复时发生什么？**
> "从 checkpoint 的 GlobalPos 接着重放到当前位置——**不需要上游重跑任何业务**，这是事件溯源最漂亮的性质：派生数据永远可以从日志追平。代价是三天的事件量要一次追完（追赶期读模型更陈旧），高吞吐场景要评估积压和追平时间。我的 CatchUp 是拉模式轮询，生产用订阅推送 + 持久化 checkpoint。"

**Q8：什么时候不该用事件溯源？**
> "四个信号：① 查询模型复杂多变——那正适合（投影自由）；② 高并发写同一聚合——CAS 重试风暴，不适合；③ 团队/组织无法承担事件不可变的心智成本（schema 演化、投影运维）——不适合；④ 数据本身就是覆盖语义（缓存、会话）——杀鸡用牛刀。我的判断框架：**事件溯源买的是'审计+时间旅行+重建自由'，卖的是'schema 刚性+最终一致+运维复杂度'**，先确认你要买的东西值这个价。"

## 对照真实系统

- EventStoreDB：原生事件数据库，流+版本号 CAS 与我的 API 几乎同构（expectedVersion）；
- Kafka 作为事件骨干：日志保留=事件存储的弱化版（保留期有限，不是永久事实）；
- Axon Framework：聚合/投影/saga 的完整框架化；
- 常见落地：电商订单、账务流水、审计场景。

## 主动承认的边界

- 全内存事件存储，无持久化/分段/归档；
- 无 upcasting（事件 schema 版本升级层）——生产最重的一块；
- 投影是同步拉模式，无独立进程/持久化 checkpoint；
- 无 saga/流程管理器（跨聚合一致性，见 Q2）。

一句话收尾："这个模块和 cdc 是一对：**cdc 说'派生数据要跟上真相'，eventsourcing 说'只要真相序列在，派生的一切都能重建'**——合起来就是 DDIA 第十二章'从事件日志出发推导状态'的完整实践。"
