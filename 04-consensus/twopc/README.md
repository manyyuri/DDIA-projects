# twopc — 两阶段提交与 Saga

> DDIA §9.3 "Atomic Commit"。这个包存在的唯一理由是让你**亲手观察到 2PC 的致命伤不是"慢"，而是"卡死"**。

## 2PC 的机制

```
阶段 1（prepare）：协调者问所有参与者"你能提交吗？"
                  参与者：取锁、写 redo log、投票 yes/no
                  yes 是一个**承诺**：从此单方面反悔就不能恢复一致性
阶段 2（commit/abort）：协调者把**唯一的决定**发给所有人
                  参与者：落盘决定、释放锁、回复 ack
```

原子性来自一件事：**决定只在协调者的那一处产生**，之后所有人都必须服从。

## 关键设计点

### 1. 参与者说 yes 之后就失去了自主权

```go
p.prepared[msg.txn] = true   // 从这一刻起，不能单方面 abort
```

这不只是代码约束。如果参与者能自己超时 abort，而协调者已经决定 commit 并且有别的参与者已经 commit 了，就会**一半提交一半回滚** —— 原子性直接破掉。

### 2. 协调者在阶段 1 之后崩溃 = 全体卡死

`TestCoordinatorCrashLeavesParticipantsInDoubt` 演示了这个场景：

```
coord.PrepareAndCrash("t3")        // 发了 prepare，收到 yes，然后死了

WaitForRecoveryTimeout(net, 5s)    // 等 5 秒

→ 三个参与者全部 InDoubt = ["t3"]，持有锁
→ 时间线里既没有 t3:commit 也没有 t3:abort
```

**等待不能解决问题。** 参与者也不能互相询问——它们处于完全相同的状态，谁都不知道决定是什么。这就是"阻塞式提交协议"的定义。

唯一的出路是协调者带着决定回来（现实中靠持久化的事务表 + 恢复流程）：

```go
revived := NewCoordinator(net, "coordinator2", ...)
revived.decide("t3", true)         // 重放决定，参与者才解锁
```

### 3. 其余两种故障也各有代价

| 故障点 | 结果 |
|---|---|
| 参与者投票 abort | 整个事务回滚，**连投了 yes 的参与者也要回滚**（决定是全局的） |
| 参与者在 prepare 之后、阶段 2 之前崩溃 | 它恢复后仍然是 in-doubt，**必须阻塞等待** |
| 协调者在阶段 2 中途崩溃 | 部分参与者已提交、部分还在等 → 系统处于**不一致的中间态**，直到决定被重放 |

`TestOneAbortVoteAbortsEveryone` 验证第一种：一票否决，所有参与者都不许 commit。

## Saga：用补偿换掉阻塞

Saga 不做两阶段，它做**一串本地事务 + 每个事务的补偿动作**：

```
Do(T1) → Do(T2) → Do(T3) 失败 → 逆序补偿 Compensate(T2) → Compensate(T1)
```

`TestSagaCompensatesOnFailure` 转账例子：扣款成功、入账成功、发通知失败 → 逆序补偿，余额回到 100/0，日志里能看到补偿顺序确实是反的。

**取舍非常干净：**

| | 2PC | Saga |
|---|---|---|
| 原子性 | 真原子（对外不可见中间态） | 最终一致，**中间态可见** |
| 隔离性 | 有锁，有隔离 | **没有隔离**（别人能看到 T1 已生效、T2 未生效） |
| 阻塞 | 协调者挂 = 全员卡死 | 不阻塞 |
| 复杂度 | 协议简单 | 每一步都要**手写补偿**，补偿可能失败、可能不可逆 |

这就解释了为什么微服务流行 Saga、而数据库内部跨分片还是用 2PC（甚至更糟的 2PC + Paxos，比如 Spanner）。

## 取舍

| 选择 | 得到 | 代价 |
|---|---|---|
| 2PC | 真原子性、有隔离 | **协调者故障 = 参与者卡死持锁**；延迟 = 两轮 RTT |
| 3PC | 理论上非阻塞 | 需要同步网络假设（超时不能误判），实际很少用 |
| Saga | 无锁、不阻塞、跨服务天然 | 无隔离、补偿要人写、中间态可见 |
| 2PC + Paxos（Spanner） | 协调者也不怕宕机 | 实现复杂度、延迟（+ 时钟不确定区间） |
| 放弃原子性（最终一致） | 最简单最快 | 上游要自己处理不一致窗口 |

## 已知边界

- 协调者没有持久化事务表，也没有恢复/重放流程（`revived` 是手工构造的）。
- 没有参与者之间的互查协议（真实系统里可以问其他参与者，但只有在"有人知道"时才安全）。
- 没有超时重传、去重（`ack` 只是一个记录，没有幂等约束）。
- Saga 没有实现"半并行"编排（parallel saga）、也没有重试策略和补偿栈的持久化。
