# INTERVIEW — cdc 讲解

## 30 秒定位

> "变更数据捕获：把上游表的变更流成下游派生视图（搜索索引、缓存、数仓）。核心难题一句话：**上游在你拷贝的同时还在变**。我做了三件关键的事：快照和变更流在同一个 LSN 上切割；变更带 before/after 双镜像；订阅端按主键幂等 upsert。schema 演化里'加列兼容、删列不兼容'也有专门测试。"

## 两分钟讲解稿

> "CDC 的初始同步是'快照+增量'：先拷全量，再 tail 变更日志。**命门在切割点**：快照完成时的位置（LSN）必须和 tail 的起点严丝合缝。我的 Snapshot 把'拷贝'和'取 LSN'放在同一个临界区，返回 (副本, lsn)，Tail 从这个 lsn 接着流。如果先拷贝后取 LSN，中间落地的写既不在快照里也可能已滑过日志位点——丢；反过来则重。因为下游是幂等的，**重是安全的、丢是致命的**，所以宁可让两边重叠。
>
> 变更结构带 before/after 两个镜像。为什么 delete 也要 before？因为下游可能从旧值派生过东西——全文索引要删掉那些词条、二级索引要删旧键。只给'主键 X 没了'，下游无法清理派生物。
>
> 幂等是订阅端唯一的硬要求：投递保证是 at-least-once，同一条 change 可能来两次，我的 View 按 LSN 去重 + 按主键 upsert。**经典 bug** 是把视图做成'每来一条 insert 就 count++'——重复投递直接把计数乘以 N。测试里同一批投三遍，OpsApplied 仍是 1。
>
> Schema 演化：加列（带默认值）向后兼容——老消费者忽略新字段；删列向后不兼容——还在 SELECT 它的消费者立刻坏。我的做法是每条 change 打上写入时的 SchemaVersion，变更日志里保留历史 schema 定义，所以 v1 时期产生的变更在 schema 升到 v2 后依然按 v1 正确解码。**没有版本号，老变更在新 schema 下解码错位**——CDC 管道最隐蔽的一类 bug。"

## 可主动抛出的数字 / 断言

- `TestBootstrapSnapshotPlusTailIsConsistent`：快照 50 行，期间再写 10 行，tail 后视图 60 行、Diff 为空
- `TestReplayingAChangeIsIdempotent`：同一批投三遍，OpsApplied 仍为 1
- `TestDropColumnBreaksNaiveConsumers`：删列后老消费者直接失败（可见的不兼容）

## 追问链

**Q1：快照和取 LSN 为什么要同一个临界区？两种顺序各丢什么？**
> "目标：快照内容 ⟺ 某个 LSN 时刻的全量，Tail(LSN+1) 补之后的一切。'先取 LSN 再快照'：LSN 之后的写进了快照（拷贝时数据已经在了）也进了流——**重**，幂等 upsert 下安全；'先快照后取 LSN'：快照完成到取 LSN 之间的写**两头都不在**——丢。所以顺序的设计原则是'宁可重叠不可留缝'，我把两个动作做成原子、直接消灭缝。真实的 Debezium 也是同理：快照时记录 binlog 位点，流从位点续。"

**Q2：为什么下游必须 upsert 而不是 append？**
> "因为 at-least-once。重复投递下 append 的视图会膨胀出错（count×3、列表重复行）。upsert 按主键覆盖，重复变成幂等。再加 LSN 单调去重双保险：乱序到达时（多分区 CDC 常见）按'只接受比已应用 LSN 新的'还能挡住回退。**派生数据的一致性模型 = 至少一次投递 + 按键幂等 + 位置去重**，三件套缺一不可。"

**Q3（追）：那 LSN 去重要求变更有全序，多主库怎么办？**
> "单主库 binlog 天然全序，LSN 好用。多主/无主系统没有全局序，只能退到'按主键+向量时钟/版本号'的因果序，或者引入全局发号器（TSO）。这就是为什么成熟 CDC 基本都寄生在单主复制日志上（MySQL binlog、Postgres 逻辑解码、MongoDB oplog）——**CDC 的前提是上游有一条全序的变更日志**，这本身就是单主架构的红利。"

**Q4：delete 带 before 我理解了，update 的两个镜像都用来干什么？**
> "before 清理派生物，after 重建派生物。例子：用户的 email 字段更新了——下游有 email→userId 的反向索引，必须用 before 的旧 email 删索引项、after 的新 email 建新的。只给 after 的话旧索引项永远残留——缓存不一致的常见来源。我的 Change 结构 insert 时 before 为 nil、delete 时 after 为 nil、update 两个都带，用测试钉死了这个契约。"

**Q5：加列为什么兼容、删列为什么不兼容？判据是什么？**
> "判据是'老消费者读新数据'和'新消费者读老数据'是否都成立（向后+向前兼容）。加列带默认值：老消费者忽略多出来的字段（schema-on-read 或按名字取），新消费者读老数据补默认值——成立。删列：老消费者的 SELECT 那一列直接不存在——破。改类型介于中间：int→string 需要 registry 做转换视图。这就是 schema registry 存在的意义：给每条数据带版本，registry 提供兼容性检查和转换，**把'不兼容'从运行时崩溃提前到发布时拒绝**。"

**Q6：重放和恢复的区别？什么场景用重放？**
> "恢复=故障后回到断点，靠 checkpoint 的 LSN 续传；重放=**故意**从 0 重来——投影代码有 bug 修好了，重建；新上搜索集群，reindex；审计需要，回放全历史。重放的安全性完全依赖幂等 upsert：我的测试跑第二遍 Replay，'不产生任何新的应用'。这也是事件溯源的思想（我下一个模块）：**只要真相序列还在，一切派生物都是可丢弃、可重建的缓存**。"

**Q7：怎么发现源和视图已经静默分歧了？**
> "持续对账。我的 Diff 全量逐主键比对（教学清晰，成本高）；生产做法：定期 checksum 分块比对（按主键范围切、哈希摘要比对，分歧块再细查）+ 抽样 + 业务侧的对账 job（比如订单数 vs 搜索可查数）。发现分歧后按 Q6 重放修复。CDC 系统的运维本质就是**永远假设会分歧，持续测量分歧，靠重放收敛**。"

**Q8：缓存一致性能用这套吗？（高频面试变形）**
> "能，CDC 就是缓存失效的正确姿势之一：binlog→消息→按主键失效/更新缓存，替代业务代码里的双写（双写没有原子性，业务失败和缓存失败无法对齐）。对比 Cache-Aside：CDC 路径的延迟高一点（毫秒到秒级最终一致），但**不会漏**——任何写路径（包括 DBA 改数、批量 job）都会被捕获，而 Cache-Aside 依赖每处代码都记得更新。代价是要维护 CDC 管道本身。我的回答框架：强一致场景 CDC 也不行（本质最终一致），高 churn 缓存要评估更新风暴。"

## 对照真实系统

- Debezium + Kafka Connect：快照模式（initial/schema_only）、binlog/逻辑解码位点切割——和我的 Bootstrap/Tail 同构；
- Canzl/Canal（阿里）：MySQL binlog 订阅，同样的镜像语义；
- 我的简化：变更日志显式实现（不解析真 WAL）、单表单视图、无多表事务边界。

## 主动承认的边界

- 不是真的解析 WAL/binlog（显式变更日志模拟）；
- 单表单视图，无跨表事务/多表 join 派生；
- registry 只记录不校验（不拒绝不兼容变更）；
- Diff 全量对账，无 checksum 增量校验、无背压/保留期管理。

一句话收尾："CDC 教我的元方法论：**和'持续变化的源'打交道，先找全序位置（LSN），再谈一致性；幂等是通往重放自由的唯一门票**。这套思路平移到缓存、索引、读副本全部成立。"
