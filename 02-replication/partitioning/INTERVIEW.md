# INTERVIEW — partitioning 讲解

## 30 秒定位

> "分区的再平衡实验。核心问题不是'怎么分'，而是**'加一个节点要搬多少数据'**。我实测：20000 个 key、3→4 节点，取模哈希搬 75%，一致性哈希只搬 23.2%；虚拟节点把负载倾斜从 1.49x 压到 1.09x。中间还踩了个真实工程的坑：FNV-1a 的低位有结构，节点环点会聚集——哈希'看起来能用'和'分布真的均匀'是两回事。"

## 两分钟讲解稿

> "取模哈希 `hash(key) % N` 完美均衡、一行代码，但 N 一变，每个 key 的归属重新洗牌——3→4 节点时只有 1/4 的 key 碰巧不变，**75% 的数据要搬家**，相当于全集群迁移一遍，这个成本让扩容变成灾难。
>
> 一致性哈希把节点和 key 都映射到一个环上，key 归属顺时针第一个节点。加一个节点，它只抢走环上自己那一段弧——理论只搬 1/(N+1)，加第 4 个节点就是 25%，我测得 23.2%，差值就是有限样本的随机波动。
>
> 但裸环有个问题：弧长是随机的，一个节点运气差分到一小段，负载可以差 49%。解法是**虚拟节点**：每个物理节点在环上放 256 个点，负载是 256 段独立随机弧长之和——独立随机变量求和，方差按 n 衰减，这就是大数定律。实测 max/avg 从 1.49x 压到 1.09x。这也是为什么生产系统用 100~1000 个 vnode。
>
> 还有一个被低估的细节：**哈希函数的雪崩性**。我一开始用原始 FNV-1a，发现 `node#0`、`node#1` 这类字符串的哈希低位保留结构，环点挤在一起，倾斜恶化到 1.31x。加一步 MurmurHash3 的 finalizer（异或移位乘魔数）就拉平了。这件事只有测了才知道——我的结论是**任何哈希分片上线前都要跑倾斜测试，而不是相信哈希函数的默认行为**。
>
> 范围分区是另一极：天然支持范围扫描，但热点 key 会打爆单个节点，修法是动态 Split/Merge——我把热 range 切两半给新节点，热度过去再合并回来。再平衡的贪心算法实测搬动次数最少：12 个 range 3→4 节点恰好搬 3 个。"

## 可主动抛出的数字

- 取模 3→4：**14990/20000 keys moved = 75.0%**（理论 3/4）
- 一致性哈希 3→4：**4642/20000 = 23.2%**（理论 1/4=25%）
- vnode：1/node → **1.49x** 倾斜；256/node → **1.09x**
- FNV-1a 裸用倾斜 **1.31x**，加 finalizer 后恢复正常
- range 再平衡：12 ranges、3→4 节点，恰好搬 3 个

## 追问链

**Q1：75% 这个数怎么推出来的？**
> "key 归属由 `hash(key) % N` 决定。3→4 时，`h % 3 == h % 4` 当且仅当 h mod 12 恰好落在 {0,1,2}∪…具体算：h%3==h%4 要求 h mod 12 ∈ {0,1,2}（即 h≡h mod 3 且 h mod 4 相同的那 3 个值），概率 3/12=1/4 保持原位，**3/4 重映射**。一般地 N→N+1 只有 ~1/(N+1) 的 key 碰巧不动——所以节点越多，取模的灾难性反而'越不明显'，但绝对迁移量依然巨大。"

**Q2（追）：一致性哈希 25% 理论值怎么来的？你的 23.2% 为什么更低？**
> "新节点在环上均匀随机落点，它接管的弧长期望是 1/(N+1)——原来归属'顺时针到下一个节点'那段的 key 全部改判。测出 23.2% 低于 25% 是有限样本 + 具体落点位置的随机偏差，换 seed 会上下浮动，量级稳定在 1/(N+1) 附近。这个实验跑 1 秒钟，但它是'为什么有一致性哈希'的完整答案。"

**Q3：虚拟节点为什么能削倾斜？数学上是什么？**
> "每个节点 1 个点时，它的负载 = 一段随机弧，方差大。放 256 个点，负载 = 256 段独立弧长之和；独立同分布求和，均值乘 256、方差乘 256，**相对波动（标准差/均值）按 √256=16 倍衰减**——中心极限定理。所以 vnode 不是玄学，是采样平均。代价是环元数据 ×256、路由表变大，以及跨 vnode 的范围查询更碎。"

**Q4：热点问题，hash 分区解决了吗？**
> "解决了一半：它让**不同 key** 均匀分布，但一个 key 本身是不可分割的最小单位——一个顶流账号还是一整个 key，哈希再均匀它也只落在一个分区。解法在 key 内部做文章：加随机后缀把写打散（`user42#0..9`），读的时候聚合 10 个后缀——两阶段聚合。或者像 ES 那样 routing 到自定义分片。范围分区的热点解法是 Split，但如果倾斜到一个 key 上，Split 也切不动，同样要加盐。"

**Q5（追）：加盐之后 per-key 的读怎么办？**
> "单点读要扇出到所有后缀（10 倍读放大），或者牺牲实时性：写打散 + 定期聚合成物化视图。所以加盐是用读换写，适合写多读少的热点。反过来的场景（读热点）用缓存/副本更合适。没有免费的午餐——每个倾斜方案都是一次明确的读写置换。"

**Q6：再平衡迁移过程中，请求怎么路由？会不会丢？**
> "经典的双写窗口协议：① 迁移开始，源和目标双写（或写源+复制），读仍走源；② 每个分片迁移完成后，路由表原子切换到目标；③ 源保留一段时间兜底后下线。Redis Cluster 用 slot 迁移的 `MIGRATING/IMPORTING` 状态就是这个流程。我的实现只算了'该搬哪些'（KeyMovement），没有搬的动作和切换协议——这是我明确列出的边界，因为**正确的迁移协议比算 key 归属难一个数量级**，那部分我通过读 Kafka 的 reassignment 和 Redis Cluster 文档补。"

**Q7：Redis Cluster 为什么用 16384 个固定 slot 而不是一致性哈希？**
> "slot 是'固定分片数'方案：分片数在系统初期定死（16384），节点只持有 slot 的映射。加节点搬的是'若干 slot 的所有权'，迁移单位小、可控、可暂停；而且 slot→node 映射可以用 bitmap 紧凑编码（16384 bit = 2KB），心跳里带得动。一致性哈希的 vnode 方案要传播整个 vnode 环。代价是 slot 数上限在创建时就锁死了——它其实是一致性哈希和固定分区的折中。"

**Q8：哈希分区和范围分区怎么选？**
> "三个问题：要范围扫描吗（时间序列、前缀查询 → range）？key 分布均匀吗（user_id 类 → hash）？有没有顺序写热点（单调递增主键 → 必须打散，否则所有写打到最后一个分区）？生产系统经常混合：Kafka 按 key 哈希分区保证 per-key 有序，TiKV 按 range 分片支持扫描、上层再靠 PD 调度热点。"

## 踩坑故事（主动讲）

**FNV-1a 低位聚集**：环倾斜一度 1.31x，排查发现 `node#0..#4` 的哈希低位模式相似，环点成堆。加 MurmurHash3 finalizer（`h ^= h>>16; h *= 0x85ebca6b; ...`）后分布拉平。教训写进了 README：**哈希函数的均匀性要用数据验证，不能凭感觉**——后来我发现 Kafka/Redis 都对 key 哈希做了 murmur 变换，同一个坑的工业解法。

## 主动承认的边界

- 无真实迁移实现（只算 key movement，无双写/切换协议）；
- `Locate` 每次二分，无 key→节点缓存；
- `AssignRanges` 是贪心非最优，无机架感知；
- vnode 无权重（大机器不能多分）。

一句话收尾："这个模块回答的是扩容的成本结构：**取模是全量迁移，一致性哈希是 1/N，固定 slot 是可控小步**——三个方案我都用 20000 个 key 量过一遍。"
