# INTERVIEW — logbroker 讲解

## 30 秒定位

> "分区日志加消费组——Kafka 的骨架。全部设计来自一句话：**offset 是消费者的位置，不是消息的属性**。这句话带来重放免费、多订阅者独立、以及'再均衡会重复投递'的全部后果。我用测试钉死了三个细节：retention 之后读旧 offset 必须报错而不是返回空；再均衡时 offset 跟着分区走；未提交的工作会被重新投递。"

## 两分钟讲解稿

> "Topic 是分区数组，分区是只追加的段序列。生产者按 key 哈希选分区——**同 key 同分区是拿到 per-key 有序的唯一方法**；空 key 轮询换吞吐，放弃顺序。这是一个显式的选择，不是默认福利。
>
> offset 的归属决定一切。传统 MQ（RabbitMQ）消息被 ack 就删，消费者重置不可能；日志 broker 不删——你消费到哪是**你自己的游标**。所以：同一个 topic 被三个组独立消费互不影响；下游出了 bug 从头重放修数；新增一个搜索集群 reindex，上游零改造。Kafka 之所以从 MQ 演化成'分布式日志'、再变成流处理的基础，根子就在这个设计。
>
> 但 retention 会推进 log start offset，这时 `Read(0)` 必须返回 **ErrOffsetOutOfRange** 而不是空——'没数据'和'数据被删了'是两个语义：前者该继续等，后者必须回落到 LogStartOffset 重新对齐，通常还要告警。返回空会让消费者把删数据当正常，静默丢一段——**静默是最糟的失败模式**，这是我全仓库反复出现的设计原则。
>
> 再均衡：offset 跟着分区走、不跟着消费者走。A 提交 offset 后退出，B 接管分区从 A 的位置继续。但窗口期的重复不可避免：**处理完、commit 之前**崩溃，接管者会重投这段——所以 Kafka 世界默认 at-least-once，'exactly once'从来不是 broker 单方面能给的属性，要么消费端幂等（我的 windowing 模块就是这么做的），要么事务把'位移提交+结果写出'原子化。"

## 可主动抛出的数字 / 断言

- `TestKeyedOrderingAndPartitionAffinity`：100 条同 key 记录同分区、offset 严格递增；空 key 至少落 2 个分区
- `TestRetentionTruncatesButOffsetsKeepClimbing`：`Read(0)` → `ErrOffsetOutOfRange`；新 offset 接着 12、13 续编，**永不复用**
- `TestRebalanceCanReplayUncommittedWork`：未提交 offset 的工作被重新投递（at-least-once 的窗口）

## 追问链

**Q1：为什么'同 key 同分区'是 per-key 有序的唯一方法？**
> "分区内是单写者追加，顺序天然成立；跨分区没有全局序——两个分区在不同 broker 上，谁也没承诺先后。所以要 per-key 有序，必须让这个 key 的所有写进同一个分区，由哈希分区保证。代价：① 分区数变化时 key 会迁移，**再均衡瞬间 per-key 顺序可能断裂**（一部分在旧分区、一部分在新分区，消费者按各自 offset 读，交错）——Kafka 的应对是保证单次 rebalance 期间语义、应用层容忍瞬时乱序或等稳定；② 热 key 打爆单分区。这两个代价我都写在取舍表里。"

**Q2（追）：那要跨 key 全局有序呢？**
> "只有两条路：单分区（放弃水平扩展，kafka 完全做得到，小流量场景就这么用）；或者全局序号+下游重排（用 HLC/全局发号器盖时间戳，消费者缓冲重排——本质是把流处理变成微型批处理）。没有第三条：**全局有序和水平扩展是数学上对立的**，问'能不能都要'就是没理解分区买的是什么。"

**Q3：为什么被删的 offset 读起来要报错？返回空有什么不对？**
> "两种语义、两种恢复动作。'空'=这段暂时没数据，消费者继续轮询等待；'越界'=这段曾经存在但被 retention 删了，消费者必须把位点重置到 LogStartOffset，并且**告警**——因为你可能丢了这段数据的处理。返回空的话消费者永远'正常'，丢数据无人知晓。我在 logbroker 和 cdc 两个模块都贯彻这条：宁可显式报错，不做静默降级。"

**Q4：消费者组 3 个成员、topic 2 个分区，会怎样？**
> "一个人分不到分区，闲着。分区是并行度上限——要 3 个消费者有用，topic 至少 3 个分区。反过来，分区数定小了，将来扩消费吞吐就到顶，**Kafka 的分区数是建 topic 时最需要前瞻的参数**（只能加不能减，加了 key 迁移乱序，见 Q1）。"

**Q5：再均衡的重复窗口具体在哪？怎么缩？**
> "窗口=『处理完→提交 offset』之间。缩小办法：① 提交粒度细一点（每 N 条而不是整批）——但频繁提交增加 broker 压力；② 处理顺序换成'先提交后处理'——窗口反向，变成**丢**数据（at-most-once），多数业务宁可重复不可丢；③ 正确答案：**消费端幂等**，重复投递无副作用。我的 windowing 模块实现了第③条：sink 按 (window,key) upsert，物理写 4 次可见状态和写 2 次完全相同。Kafka 的 EOS 是把'读位移+写结果'放进一个事务，思路是同一件事的 broker 侧版本。"

**Q6（追）：那 Kafka 的 exactly-once 到底保证什么、不保证什么？**
> "保证：consume-transform-produce 链路原子——消费的位移提交和产出的消息在同一个事务里，崩溃重启后不会重复产出。不保证：**对 Kafka 之外的世界**——你的处理器写外部数据库、发 HTTP 请求，事务罩不住，还是要幂等或两阶段。所以面试的标准答案：exactly-once 是'至少一次投递+原子位移+幂等/事务 sink'的组合拳，**没有魔法**。我的两个模块（logbroker 的 at-least-once + windowing 的幂等 sink）合起来就是这个语义的分解教学。"

**Q7：为什么用整段删除而不是逐条删？**
> "段是顺序追加的单位，删也按单位删：删一个段文件是 O(1) 的元数据操作（unlink），逐条删需要原地整理随机写，把顺序写的引擎变成随机写的引擎。代价是删除粒度粗（最后一段没满不能删）——所以 Kafka 攒段、按时间/大小滚动。compaction topic（按 key 保留最新值）是另一套，用 LSM 式的后台整理而不是删除，我列在边界里没实现。"

**Q8：和 RabbitMQ 这类传统 MQ 的本质区别？**
> "三点：① **消费模型**——拉+游标 vs 推+ack 删除；② **保留策略**——时间/大小保留 vs 消费即删，日志 broker 把'存'和'消费'解耦，这是重放、多订阅、回溯的来源；③ **顺序**——分区内有序 vs 队列级有序（单队列吞吐低）。代价是 Kafka 的删除语义粗、单条延迟不如推式 MQ 低。选型口诀：**事件管道/流处理选日志，任务分发/路由选 MQ**。"

## 对照真实系统

- Kafka：ISR 副本 + controller 协调 rebalance（generation fencing 防僵尸成员）、cooperative-sticky 策略、事务与幂等生产者；
- 我实现的简化：range 分配、同步模拟 rebalance、无副本、无事务。

## 主动承认的边界

- 无组协调协议（leader 选举、会合、代际 fencing），rebalance 是同步模拟；
- 只有 range 分配（无 round-robin/sticky/cooperative）；
- retention 手动触发，无按时间/大小自动策略；
- 分区无副本容错、无生产者幂等、无 compaction topic。

一句话收尾："这个模块把我对消息系统的理解从'队列'升级到'日志'：**offset 归属决定语义谱系**——归属消费者才有重放和独立订阅，也才有 at-least-once 的必然性。"
