# partitioning — 分区与再平衡

> DDIA §6。分区买来扩展性，代价是跨分区没有顺序、没有事务。这一章真正会咬人的地方不是"怎么分"，而是**"加一个节点要搬多少数据"**。

## 机制

两种策略，两种失效模式：

| | 哈希分区 | 范围分区 |
|---|---|---|
| 负载均衡 | 天然均匀 | 热点 key 会打成热节点 |
| 范围扫描 | 做不到 | 天然支持（数据有序） |
| 再平衡代价 | 一致性哈希搬 ~1/(N+1) | 搬最少的 range |
| 典型系统 | Dynamo、Cassandra、Redis Cluster | Bigtable、HBase、TiKV、Spanner |

## 关键设计点

### 1. 取模哈希是一个陷阱

`node = hash(key) % N` 完美均衡、无状态、实现一行。**但 N 一变，几乎所有 key 都要搬家。**

实测（20000 个 key，3 节点 → 4 节点）：

```
modulo hashing:      14990 keys moved (75.0%)      ← 理论值 3/4
consistent hashing:   4642 keys moved (23.2%)      ← 理论值 1/4
```

一致性哈希的做法是把节点和 key 都映射到一个环上，key 归属"顺时针第一个节点"。加一个节点只会抢走它自己那一段弧——**只有那一段的 key 会搬家**，其余原封不动。`TestRemovingANodeKeepsOtherAssignments` 验证了删除节点时同样只影响它自己的 key。

### 2. 虚拟节点解决"环上的随机性"

每个节点在环上放 1 个点时，弧长是随机的，负载可以差 49%：`1 vnode/node → max/avg = 1.49x`。

给每个节点放 256 个虚拟节点后：`256 vnodes/node → 1.09x`。

原理很朴素：**独立随机变量的和，方差按 n 衰减**。这也是为什么真实系统用 100~1000 个 vnode。

### 3. 一个被低估的细节：哈希函数的雪崩效应

实现里 `hash32` 在 FNV-1a 之后加了一步 MurmurHash3 的 finalizer。这不是装饰：

> 原始 FNV-1a 的低位保留结构，导致 `node#0`、`node#1`… 生成的环点会**聚集**在一起，实测倾斜从 1.05x 恶化到 1.31x。

加一步 `h ^= h>>16; h *= 0x85ebca6b; …` 就好了。**哈希函数的"看起来能用"和"分布真的均匀"是两件事，只有测了才知道。**

### 4. Range 的拆分与合并

范围分区里修热点的方法是**拆**，不是搬：

```go
p.Split("k02500", "n3")   // 把热 range 切成两半，一半给新节点
p.MergeRange(2)           // 热度过去之后合并回来
```

`AssignRanges` 是贪心再平衡：从超过目标的节点往不足的节点搬，**搬动次数即最小**。实测 12 个 range、3 → 4 节点，恰好搬 3 个（每个节点应有 3 个 range，新节点要拿 3 个）。

## 取舍

| 选择 | 得到 | 代价 |
|---|---|---|
| 哈希分区 | 负载均匀，再平衡搬得少 | 没有范围扫描；相邻 key 不在一台机器上 |
| 范围分区 | 范围扫描 + 局部性 | 热点 key → 热节点，要拆分才缓解 |
| 一致性哈希 | 加/删节点只搬 ~1/N | 环维护、vnode 元数据；跨节点范围查询更麻烦 |
| 固定分片数（如 Redis Cluster 的 16384 slot） | 迁移单位小、可控 | 需要一层 slot→节点的映射 |

## 自测题

1. 为什么取模哈希加一个节点要搬 ~(N-1)/N 的数据？用 N=3→4 推导一下 75% 这个数。
2. 一致性哈希的理论值为什么是 1/(N+1)？测试测得 23.2% 而对 4 个节点是 1/4=25%，差值从哪来？
3. 虚拟节点为什么能削倾斜？把 vnode 数从 256 降到 16，预计倾斜变成多少？
4. 范围分区里，如果**同一个热 key** 被打爆（比如某个明星的微博 ID），`Split` 能解决吗？解决不了的话还有什么办法？（提示：加随机后缀做两级聚合）
5. 再平衡时"搬数据"的时间窗口里，读请求应该走旧节点还是新节点？怎么保证不丢不重？

## 已知边界

- `Locate` 每次都做一次二分（没有缓存 key→节点），高频路径需要一层映射缓存。
- `AssignRanges` 是贪心，不是最优解；也没有考虑机架/可用区感知。
- 没有真正的数据迁移实现（只算了"该搬哪些"，没有搬的动作、双写窗口、切换协议）。
- 哈希环的实现里同一节点的 vnode 没有做"节点权重"（大机器多分点）。
