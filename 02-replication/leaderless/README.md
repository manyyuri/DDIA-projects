# leaderless — 无主复制（Dynamo 式）

> DDIA §5.5。不选 leader，用 W + R > N 的**集合重叠**换取一致性；代价是并发写会产生**冲突**，而冲突必须由应用合并。

## 机制

```
写：coordinator 先读 R 个副本 → 合并它们看到的因果历史 → 递增自己的计数器
    → 写 W 个活着的偏好列表节点；对宕机的节点留 hint（sloppy quorum）
读：读 R 个副本 → 合并 → 把最新的写回给落后者（read repair）
    → 若存在互不包含的版本，返回多个值（siblings）
```

偏好列表用哈希环给每个 key 挑起点，所以相邻 key 不会压在同一个集合上。

## 关键设计点

### 1. 向量时钟：区分"更新"和"冲突"

这是整个包的核心。一个 `VectorClock` 是 `{节点: 计数}`：

| Compare 结果 | 含义 | 动作 |
|---|---|---|
| `After` | 因果更新 | 丢掉旧的 |
| `Before` | 被更新 | 保留现有的 |
| `Concurrent` | **并发写** | 两个都留 = siblings |
| `Equal` | 同一次写 | 去重 |

`addVersion` 就是这么实现的：新版本吞掉被它支配的，遇到支配它的就整体放弃，遇到并发的就并存。

### 2. 三种"把副本拉回来"的机制，作用在不同时间尺度

| 机制 | 何时触发 | 修什么 | 代价 |
|---|---|---|---|
| **Read repair** | 读的时候 | 读到的副本之间的差异 | 读路径变重（Cassandra 改成异步 digest） |
| **Hinted handoff** | 节点恢复时 | 宕机期间**错过**的写 | 占其他节点的空间；hint 可能过期 |
| **Anti-entropy** | 后台周期 | 静默分歧（没有任何读碰到的） | 很慢，通常配 Merkle tree 才实用 |

测试里三条路径各有一个用例。注意 `TestReadRepairHealsStaleReplica` 一开始失败，因为 hinted handoff 已经把副本治好了——这恰好说明两个机制会重叠。

### 3. 删除必须是墓碑

删掉本地的版本会让"没见过删除"的副本在下一次反熵时把老值**复活**。所以删除是一条把 `Deleted=true` 的新版本。

### 4. Quorum 不是共识

W+R>N 只保证**集合相交**，它给不了你：

- **顺序**（没有全局时间，只有因果）；
- **原子性**（跨多个 key 的写没有事务）；
- **活性**（网络分区时可能两边都拿不到 quorum）。

`TestWPlusRNotGreaterThanNCanMissWrites` 演示了反向：W=1、R=1、N=3 时，读**静默返回空**，没有错误、没有冲突——这是最糟的失败模式。

## 实验

```bash
go test ./02-replication/leaderless/ -v -count=1     # 8 个测试
```

**关键场景（N=3, W=2, R=2）：**

- 写通过 n1、读通过 n2 → 一定读到（写集合 {n1,n2或n3} 与读集合 {n2,n3} 必然相交）；
- 并发写 → `siblings surfaced to the application: [apple banana]`，`conflict=true`；
- 后续一次写观察到两个 sibling，于是它的时钟同时支配两者 → 冲突被消解。

## 取舍

| 选择 | 得到 | 代价 |
|---|---|---|
| 无 leader | 没有 failover 停顿，任何节点都能接请求 | 没有顺序保证，没有"最新值"的权威定义 |
| 向量时钟 | 精确区分更新与冲突 | 时钟大小 O(节点数)，随参与节点数增长 |
| Siblings | 不丢写 | **应用必须自己写合并逻辑**（这是 Dynamo 最难的落地部分） |
| Sloppy quorum | 分区时仍可写 | 数据可能写在"不该拥有它"的节点上 |
| 读修复 | 读路径自愈 | 读延迟 = R 个副本的最慢者 |

## 自测题

1. N=3、W=2、R=2 时，写集合和读集合为什么**必然**相交？用 N=4、W=2、R=2 反推一下会怎样？
2. `siblings` 出现之后，谁是"正确答案"？为什么这个决定不能由数据库做？
3. 只靠读修复能保证最终一致吗？（提示：想想一个从没被读到的 key）
4. 向量时钟在 100 个节点的集群里会变成什么问题？生产系统通常怎么绕开？（提示：想想"最后写入者胜"丢了什么）

## 已知边界

- 读修复对**所有**偏好节点做全量推送，不是 digest 比对。
- 反熵是 O(N²) 全量对账，没有 Merkle tree 分层比较。
- 没有反熵的限速/调度，需要手动触发。
- 偏好列表只做哈希起点旋转，没有真正的"机架感知"放置。
