# INTERVIEW — twopc 讲解

## 30 秒定位

> "2PC 加 Saga 的实现，这个模块存在的唯一理由是让你**亲眼看到 2PC 的致命伤不是慢，而是卡死**：协调者在 prepare 之后崩溃，所有参与者持有锁进入 in-doubt，等 5 秒、50 秒都解决不了——参与者互问也没用，因为它们状态完全相同，谁都不知道决定是什么。Saga 用补偿换掉这个阻塞，代价是没有隔离、中间态可见。"

## 两分钟讲解稿

> "2PC 的原子性只来自一件事：**决定只在协调者一处产生**。阶段 1，协调者问所有人'能提交吗'；参与者投票 yes 的瞬间做了一个不可反悔的承诺——写 redo log、持锁，从此单方面 abort 的权利被没收。阶段 2，协调者把唯一的决定广播，所有人服从。
>
> 为什么 yes 之后不能反悔？假设参与者 A 能超时 abort，而协调者已经决定 commit 并且 B 已经 commit 了——A 再 abort，一半提交一半回滚，原子性破了。所以**参与者必须把'悬置'作为正确状态接受**。
>
> 于是致命伤来了：协调者在收到全部 yes 之后、发出决定之前崩溃——`TestCoordinatorCrashLeavesParticipantsInDoubt` 精确复现这个点，等 5 秒，三个参与者全部 InDoubt 持锁。这不是实现偷懒，是协议的数学性质：**阻塞式原子提交协议**。唯一的出路是协调者带着决定回来——真实的做法是协调者把事务表持久化，恢复进程重放决定。
>
> Saga 走另一条路：一串本地事务，每步配一个补偿，失败就逆序补偿回去。我的转账测试：扣款成功、入账成功、发通知失败 → 逆序补偿，余额精确回到 100/0。取舍很干净：2PC 是真原子、有隔离、会卡死；Saga 不阻塞、天然跨服务，**但没有隔离**——别人能看到 T1 生效 T2 未生效的中间态，每一步补偿都要手写、可能失败、可能不可逆。这就解释了为什么微服务世界选 Saga、数据库内部跨分片仍然用 2PC。"

## 可主动抛出的数字 / 断言

- `TestCoordinatorCrashLeavesParticipantsInDoubt`：等待 5s 后仍全员 InDoubt 持锁；`revived.decide("t3", true)` 重放决定才解锁
- `TestOneAbortVoteAbortsEveryone`：一票 no，全员 abort（包括投了 yes 的）
- `TestSagaCompensatesOnFailure`：补偿逆序执行，余额回到初始

## 追问链

**Q1：参与者投了 yes 之后为什么不能超时 abort？给我具体场景。**
> "三参与者 A/B/C。协调者收齐 yes、决定 commit、发给 A——A commit 了。此刻协调者崩、消息到 C 之前网络断。如果 C 有'超时自动 abort'，C 回滚了；A 已提交。同一个事务一半 commit 一半 rollback，原子性永久破坏（没有任何机制能再把它们对齐——A 的锁已经释放、数据已经被别人读了）。所以协议规定：**in-doubt 状态必须无限期持有锁等决定**。锁持有是安全的代价，不是实现瑕疵。"

**Q2（追）：那参与者互相询问不行吗？**
> "只有在'有人知道答案'时才行。如果协调者崩在决定之前，所有活着的参与者状态完全相同（prepared、没有决定）——互问得到的是彼此的沉默。真实的改进是让参与者把 prepare 状态写到**共享存储**（如 MySQL 的 xa recover 能列出 prepared 的事务，DBA/恢复工具代行协调者职能），本质还是'决定必须有一个权威来源'。我的实现里 revived coordinator 手工重放决定，模拟的就是持久化事务表的恢复流程。"

**Q3：3PC 不是号称非阻塞吗？为什么没人用？**
> "3PC 加了 pre-commit 阶段和'参与者可以按状态推断结果'的规则，但它依赖一个致命假设：**超时可以区分'对方挂了'和'网络慢'**——即同步网络模型。真实异步网络里，'协调者没响应'可能是它崩了、也可能是消息延迟；3PC 的推断在消息迟到时会产生分叉决定（一边 commit 一边 abort）。而且它三轮 RTT 更慢、还有脑裂问题。工程界的答案是放弃协议层面的完美，用**共识复制协调者状态**（2PC + Paxos 的决定日志 = Spanner/Paxos Commit 的思路）——协调者不怕崩，参与者就不用等了。"

**Q4：Saga 的补偿失败了怎么办？**
> "补偿本身必须**幂等且可重试**——它和正向操作一样会遇故障。重试穷尽后进入终态处理：死信队列 + 对账 + 人工介入。所以 Saga 的完整实现需要：补偿幂等设计、重试策略、状态持久化（每步执行到哪了）、以及一整套对账工具。我的实现是同步顺序执行 + 逆序补偿的骨架，持久化和死信是我明确列的边界。顺带一提：有些操作天然不可补偿（发出去的短信、扣掉的库存给第三方），那就要**把不可补偿的步骤排在最后**，或者引入两阶段的'预留-确认'（TCC）。"

**Q5：为什么跨微服务用 Saga，同库跨分片用 2PC？**
> "分界线是**锁和协调的信任半径**。同一数据库内：参与者行为可控、锁是本地资源、协调者写事务表和参与者落盘在同一故障域里，2PC 的阻塞窗口小且可运维。跨微服务：服务各自独立数据库、独立部署节奏，2PC 要跨网络持有别人的锁——任何一个参与者的抖动都会传染到所有人，可用性是乘法（5 个 99.9% 的服务串起来只剩 99.5%）。Saga 把长事务拆成本地短事务，没有跨服务锁，代价是中间态可见 + 补偿复杂度。一句话：**锁不出数据库，就不怕 2PC；锁要出数据库，就得用补偿。**"

**Q6：Kafka 的事务和 2PC 什么关系？**
> "Kafka 事务解决的是'consume-transform-produce 的原子性'：把'消费位移提交 + 若干消息写出'做进同一个原子写——它本质是把事务状态和消息日志合并存储，协调者（transaction coordinator）自己的状态靠 Raft 复制。所以它是'2PC 的思想 + 日志原子性 + 共识复制协调者'的组合，避免了参与者 in-doubt（消费者的位移也是日志里的一条记录）。这也是现代系统对 2PC 的普遍改造方向：**把协调者单点用共识层做高可用**。"

**Q7：XA 事务实际用过多吗？有什么坑？**
> "坑主要在工程侧：① 锁窗口长——prepare 后的行锁要等到决定到达，跨库 RTT 期间主业务表被锁；② 协调者（应用服务器）崩溃后的悬挂事务，MySQL 要手动 xa recover；③ 主流连接池/ORM 对 XA 支持稀烂，连接泄漏频发。所以国内电商普遍走'本地消息表 + 最终一致'或 TCC——本质都是 Saga 家族。我在讲这个话题时喜欢先讲我实现的 in-doubt 测试：**先把'为什么大家逃离 2PC'用 5 秒等待具象化**，再讲方案谱系。"

## 对照真实系统

- Spanner：2PC + Paxos——协调者决定被共识复制，参与者是 Paxos 组；
- Seata AT/TCC、Uber Cadence/Temporal：Saga 的工程化（编排、状态持久化、补偿重试）；
- Kafka transaction coordinator：原子提交 + 共识复制协调者的现代混合。

## 主动承认的边界

- 协调者无持久化事务表（revived 是手工构造的，模拟恢复流程）；
- 无参与者互查协议；
- Saga 无并行编排、无重试/死信、补偿栈不持久化；
- 无真实锁资源（用 InDoubt 列表模拟持锁）。

一句话收尾："这个模块的价值是把'2PC 慢'这个流行误解纠正成'**2PC 卡**'——慢是延迟问题，卡是可用性问题，后者才是架构师逃离它的原因。等 5 秒仍 in-doubt 那个测试，是我讲分布式事务时最爱放的'一段代码'。"
