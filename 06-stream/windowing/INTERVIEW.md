# INTERVIEW — windowing 讲解

## 30 秒定位

> "事件时间流处理：窗口分配、水位线、迟到三档处理、幂等 sink。核心三句话：**处理时间不等于事件时间；你永远无法确定一个窗口收完了；迟到是常态**。最硬的测试：同一批事件乱序到达和顺序到达，产出完全相同的结果——只有按事件时间开窗，重放才可复现。我在迟到判定上踩过一个真 bug：第一版用事件时间戳判定而不是水位线，窗口状态清理了还在更新它。"

## 两分钟讲解稿

> "每个事件带时间戳，事件进入一个或多个窗口（tumbling 一个、sliding 多个），累加进 pane。**水位线 = 见过的最大事件时间 − 允许乱序界限**，它是一句赌注：'我赌不会再收到比这更老的事件了'。水位线推进过窗口结束，窗口发射。
>
> 为什么必须事件时间？我的测试：同一批事件，`1,2,3,4,5` 到和 `5,1,4,2,3` 到，**产出逐字段相同**。如果按处理时间开窗，到达顺序决定归属，两次结果天差地别，重放复现无从谈起。所有流处理引擎花大力气支持事件时间，就是为了这个'确定性'。
>
> 但水位线是赌注，赌输的就是迟到数据，三档处理：水位线没过窗口结束——正常累加；过了结束但没过'结束+允许迟到'——**更新已发射的结果**（revision 2，撤回重发语义）；超过侧输出（dead letter）。为什么侧输出而不是丢弃？**静默丢数据是最糟的失败模式**，侧输出让'有多少事件没进结果'可见，这个数字通常就是'乱序界限设小了'的告警信号。
>
> 最后是 exactly-once 的真相：我用共享 sink 把整个流程跑两遍，模拟'写成功了但 offset 没提交，重启重放'——物理写 4 次，可见状态和写 2 次**完全相同**。实现就是按 (window, key) 幂等 upsert。所以 **exactly-once = at-least-once 投递 + 幂等写入**，它不是把投递做成恰好一次——分布式里做不到——而是让重复投递不产生副作用。"

## 可主动抛出的数字 / 断言

- `TestOutOfOrderWithinBoundIsEquivalentToInOrder`：乱序与顺序到达，结果逐字段相同
- `TestLateEventWithinAllowedLatenessUpdatesResult`：`result corrected from 1 to 11 (revision 2)`
- `TestTooLateEventGoesToSideOutput`：`dead letter: a@12:00:02=99.0`，99 未混进任何已发射结果
- `TestReplayIsIdempotentAtTheSink`：物理写 **2→4 次**，可见状态不变

## 追问链

**Q1：水位线为什么不能精确判断'窗口收完了'？**
> "因为'收完了'是个负命题：'从此不会再有更老的事件'——负命题没法被观测证实，只能被证伪（一个迟到事件就证伪）。水位线用'最大事件时间−界限'做启发式赌注，把赌注的成本显式化：界限大→结果完整但延迟高；界限小→快但更多侧输出。没有正确答案，只有业务能接受的延迟/完整性交换，所以它是参数而不是常量。"

**Q2：你踩的那个迟到判定 bug，具体讲讲。**
> "第一版判定'这条事件迟到了吗'用的是**事件自身的时间戳**：事件时间超过'窗口结束+允许迟到'就算无救。错在哪：窗口状态的清理时机是水位线驱动的——水位线过了'结束+允许迟到'就把 pane 删了。事件时间戳和水位线是两个时钟：一个事件的时间戳可能'还来得及'，但水位线早就把状态清了；反过来事件时间戳显示'太晚'、状态其实还在。第一版出现过'窗口状态已删、却还在往里加数据'的崩溃。修法就一条：**判定和清理必须用同一个时钟**——都用水位线。这个 bug 让我记住一条通则：一个系统里每引入一种'时间'，就要检查所有涉及状态生命周期的决策是否都统一到同一时钟。"

**Q3（追）：那 MaxOutOfOrderness 和 allowedLateness 是什么关系？为什么两个参数？**
> "作用于不同阶段：MaxOutOfOrderness 决定**什么时候第一次发射**（延迟换完整性，发射前乱序免费修正）；allowedLateness 决定**发射后还能改多久**（状态保留多久接受 revision）。第二个参数的本质是'修正窗口的长度'，越长下游收到越多 revision，状态成本越大。Flink 的 API 也是这两个参数，语义一致。"

**Q4：revision（撤回）为什么必要？下游只支持 append 会怎样？**
> "迟到更新已经发射的结果，必须'减旧值、加新值'。如果下游只支持 append（比如只 INSERT 的表），它会把 revision 2 当新纪录——**窗口和被算成 3**（1+11），比丢数据更糟。所以下游必须支持 upsert，或显式的 retraction 流（-11 +21 这种对账语义）。这也是选 sink 时最容易忽略的约束：不是所有存储都能当流处理的结果表。"

**Q5：幂等 sink 的主键怎么设计？只用业务 key 行不行？**
> "不行，必须是 (window, key)。只有 key 的话，两个窗口的同 key 结果互相覆盖——每个小时窗的计数互相冲掉。这个主键设计其实就是'把窗口标识物化成存储主键'。再进一步的问题：窗口是无限的，主键空间无限膨胀——生产上要配 sink 侧的 TTL/分区清理，或者用支持 retract 的存储。我的实现 `Upsert(window|key, sum)` 把这件事做到了最直白。"

**Q6（追）：如果下游是个聚合的聚合（二级聚合）呢？**
> "一级聚合的 revision 到了二级就得变成 retract+insert：先减去旧的一级值、再加新值。级联下去每一级都要能处理撤回。这正是 Flink 把 retract 流做成一等公民的原因——动态表（dynamic table）理论：流是表 changelog 的无限序列。我的实现用 Revision 字段模拟 changelog 协议，没做真正的减法下发，这是我列的边界。"

**Q7：空转分区问题你怎么看？（没实现但要能答）**
> "我的 WatermarkGenerator 只看本流的最大事件时间。分布式里全局水位线 = min(所有分区水位线)——**一个没数据的分区会把全局水位线永远卡住**，所有窗口不发射。解法：空闲源检测（Flink 的 idle source），一段时间没数据就把该分区标 idle、剔除出 min 计算。我列在已知边界里，但这个坑的机理我能讲：全局进度由最慢者决定，流处理里'没消息'本身也是一种要处理的信号。"

**Q8：checkpoint 里为什么存水位线？**
> "恢复后水位线必须精确还原到故障前，否则重放的事件会按错误的水位线判定迟到——状态和时钟一起回退才一致。我的 Checkpoint 存水位线+活跃 pane；Flink 的 barrier 对齐保证算子状态和输入位点原子。这背后还是那个原则：**流处理的一致性=状态+时钟+位点三者原子**，缺一个就重放出错。"

## 对照真实系统

- Flink：event time/watermark/allowedLateness/side output 的完整工业实现 + checkpoint barrier（Chandy-Lamport 变体）；
- Kafka Streams：弃用事件时间水印（KIP）转向按记录时间戳的处理，window store 按窗口分段；
- 我的实现：单机内存算子，Checkpoint 不持久化。

## 主动承认的边界

- 无分布式状态、无持久化 checkpoint/恢复；
- 无空转分区处理（全局水位线卡住的坑我知其所以然，见 Q7）；
- 无 session window 合并、无 early/late 自定义 trigger；
- retraction 只有 Revision 标记，无真实减法下发；
- 无背压。

一句话收尾："这个模块 + logbroker 合起来，我能把'流处理的 exactly-once'从口号拆解成机制链：**事件时间保证可复现，水位线显式化延迟成本，幂等 sink 承接重复投递**——三层各付各的代价。"
