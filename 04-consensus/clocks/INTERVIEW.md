# INTERVIEW — clocks 讲解

## 30 秒定位

> "四种时钟的能力阶梯：Lamport、向量时钟、HLC、Snowflake。核心认识一句话：**分布式系统里你无法相信任何一台机器的墙钟，但每个替代方案都在用不同的代价换回一部分'时间'的能力**。我每个都实现了、每个都测了它的失败场景：HLC 在墙钟回拨一小时后依然严格递增；Snowflake 回拨时拒绝发号而不是发重复号。"

## 两分钟讲解稿

> "Lamport 时钟：每次事件 `L = max(L, remote) + 1`，保证 a 因果先于 b 则 L(a) < L(b)。**但反过来不成立**——L(a) < L(b) 时 a、b 可能根本是并发的。这个单向性是它全部的局限：它能给事件编号，但不能用来判冲突。
>
> 向量时钟补上这个洞：每个节点一个分量，逐节点取 max 比较，两边各有更大分量就是 Concurrent。我在 leaderless 模块里就是靠它区分'更新'和'冲突'的。代价是 O(节点数) 的大小。
>
> HLC 是混合方案：{物理部分, 逻辑部分}。墙钟正常时物理部分跟墙钟走；墙钟回拨时逻辑部分 +1 兜底。我的测试把墙钟往回拨**一小时**，HLC 产出的时间戳依然严格递增；等真实时间追回来后重新跟随墙钟。这让它同时拿到两个好处：**单调递增 + 近似物理时间**——可以当排序键，还能做'查最近一小时'的区间查询。CockroachDB 的事务时间戳就是 HLC。还有一个关键设计：收到远端时间戳如果比本地墙钟快出**偏移上限**（我设的量级内），直接报错拒绝吸收——因为一个快 5 秒的坏钟会把整个集群的时间拖到未来。
>
> Snowflake 是另一个问题：不表达因果，只要'可排序 + 全局唯一'。41 位毫秒 + 10 位机器号 + 12 位序列。我的关键决策：**墙钟回拨时返回错误拒绝发号**，而不是阻塞或发可能重复的号——'宁可短暂不可用，绝不重复'。另一个合法选择是阻塞等到 lastMillis（Twitter 官方实现），两个都对，但必须选一个并说清理由。"

## 可主动抛出的数字 / 断言

- `TestHLCSurvivesBackwardsClock`：回拨 **1 小时**，三个时间戳严格递增
- `TestSnowflakeUniquenessAndRollback`：5000 个号无重复且严格递增；回拨后报错
- `TestLamportRespectsCausality`：并发事件被排出先后——但这个顺序是任意的
- `TestHLCRejectsExcessiveSkew`：5 秒偏移被拒，100ms 被接受并前拽本地时钟

## 追问链

**Q1：举一个 L(a) < L(b) 但 a、b 并发的具体例子。**
> "节点 A 本地 tick 两次：L=1、L=2。节点 B 完全独立地 tick 两次：L=1、L=2（初值相同时 A 的 L=1 和 B 的 L=2 毫无关系）。任何跨节点的 L 比较都没有因果含义——Lamport 只保证'因果 ⟹ 小'，用它做全序等于把任意顺序合法化了。所以它不能做 MVCC 时间戳：两个并发写会拿到有先后的时间戳，后写覆盖先写，冲突被静默解决——丢写。"

**Q2：向量时钟 O(N)，生产怎么活？**
> "三条路：① 压缩表示——dotted version vector，只记'真正相关的节点'的分量；② 截断——只保留最近 k 个 coordinator 的分量，超龄合并，损失一点检测精度换常数上限（Cassandra 的做法变体）；③ 放弃精确并发检测，last-write-wins 用时间戳强加全序——Dynamo 后来和 Cassandra 都这么选了，代价是丢并发写。我在 leaderless 里保留了完整向量，教学清晰；生产选型时我会先问'冲突丢失的业务代价有多大'再决定。"

**Q3（追）：LWW 具体丢什么？**
> "丢的是**因果上不旧于对方的写**。两个并发写，时间戳晚的那个赢——但'时间戳晚'和'内容更该赢'没有必然关系，尤其 NTP 抖动下墙钟可以乱序。安全用法是 LWW + 冲突上抛（重要字段）或者 CRDT（结构化数据），纯 LWW 只适合'覆盖语义本来就成立'的字段，比如缓存。"

**Q4：HLC 和 Lamport 本质区别是什么？**
> "Lamport 的计数器是纯逻辑的，物理上无意义；HLC 把'墙钟读数'嵌进物理部分，逻辑部分只做回拨兜底。收益是 HLC 时间戳**可以和真实时间做近似比较**——'最近一小时的数据'这种查询能跑，误差是时钟偏移界。CockroachDB 靠这个把事务时间戳和区间扫描统一了。代价是它依然需要偏移上界的假设，超界的消息必须拒绝——否则一个坏钟污染全集群。"

**Q5（追）：为什么拒绝而不是把偏移吸收进来？**
> "吸收 = 本地把物理部分推到远端值。如果远端钟快了 5 秒，我吸收后自己的时间戳也在未来；它再广播，全网被拖快 5 秒。所有依赖'时间戳 ≈ 真实时间'的语义（lease 到期、TTL、日志对齐）集体错位。拒绝则把故障隔离在单节点：它发的时间戳别人不信，但别人的时间线不脏。这是'故障遏制'思想——错误要就地暴露，不能顺着数据流传播。"

**Q6：Spanner 为什么不用 HLC，要搞原子钟？**
> "Spanner 要的是**外部一致性**：事务 T1 在 T2 开始前完整提交，则 T1 的时间戳必须真的小于 T2——不管观察者在哪。HLC 做不到：两个不相通信的节点的 HLC 物理部分可以乱序于真实时间。Spanner 的 TrueTime API 返回 [earliest, latest] 区间——'现在'是一个不确定区间；Commit-Wait 让事务等到'提交时间戳 < 现在的 earliest'才对外可见，用等待换掉不确定性。原子钟/GPS 只是把区间收窄到几毫秒，让等待可承受。所以不是 HLC 不够好，是**目标保证不同**：CRDB 的 HLC 给 serializability + 近似物理序，Spanner 给 strict serializability。"

**Q7：Snowflake 回拨你选了报错，什么场景该选阻塞等待？**
> "我的选择（报错）适合'ID 唯一性是硬约束、短暂发不出号可接受'——比如订单号，重复是事故，慢一点是抖动。阻塞等待适合'可用性优先、且回拨通常只有几毫秒'——Twitter 官方实现，NTP 微调时挡一下就过去了。但阻塞有上限问题：回拨 1 小时你阻塞 1 小时吗？所以要配告警 + 人工介入路径。关键是**两个都对，但不选就是错**——默认行为必须显式设计。我的测试里 5000 个号零重复、严格递增，就是给'报错'这个选择背书。"

**Q8（追）：机器号怎么分配？**
> "我的实现假设预分配。生产上：固定配置（小集群）、ZooKeeper/etcd 顺序节点租约（大集群）、K8s 下用 StatefulSet 序号。这个'ID 服务的依赖'是 Snowflake 常被忽视的脆弱点——发号依赖的元服务本身要高可用，否则雪崩。"

## 对照真实系统

- CockroachDB：HLC + maxOffset（500ms 量级）+ 超界节点自杀——我的拒绝策略同源；
- Spanner：TrueTime + Commit-Wait，花钱（原子钟）买严格外部一致；
- DynamoDB/Cassandra：LWW 时间戳（向量时钟被放弃的工程取舍）；
- Twitter Snowflake / 美团 Leaf：回拨策略差异是面试高频考点。

## 主动承认的边界

- 向量时钟无 dot/差量压缩；
- HLC 无 Commit-Wait（那需要 TrueTime 语义）；
- Snowflake 无机器号分配服务；
- 只有被动拒绝偏移，无 NTP 主动测量。

一句话收尾："这个模块让我把'时间'从一个直觉概念拆成了**四种能力各异的工具**——选型时先问'我要时间回答什么问题'：排序、因果、近似物理时刻、还是只要唯一。"
