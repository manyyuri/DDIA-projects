# INTERVIEW — bitcask 讲解

## 30 秒定位

> "bitcask 是最简单的能用存储引擎：磁盘上只有追加日志，内存里一张哈希表 KeyDir 记每个 key 最后一次写的位置。点查 O(1) 没有读放大，代价是全量 merge 重写、不能范围扫描。我用它把'日志是真相、索引是缓存'这件事彻底搞清楚了——包括崩溃恢复怎么区分撕裂写和静默损坏，这是这个项目里我最得意的设计点。"

## 两分钟讲解稿

> "核心数据结构就一句话：**写路径是追加一条带 CRC 的记录，然后更新内存里的 KeyDir；读路径是查 KeyDir 做一次 pread**。所以点查是 O(1)，没有任何读放大，这对缓存、会话这类点查场景非常合适。
>
> 但它的代价我全部测出来了。1000 次覆盖写同一个 key，落盘是 1000 条完整记录——逻辑写 256KB、实际落盘 272KB，**写放大 1.06x**，但注意空间放大是 1000 倍，一条 256 字节的数据在 merge 前占了 256KB。空间回收只能靠 merge：把存活记录抄进新段、删旧段。merge 是可中断可重入的——新段 id 取最大，恢复时按 id 顺序重放、同 key 后者胜，所以合到一半崩了，结果依然正确，我写了 `TestMergeIsCrashSafe` 手工构造中间态验证。
>
> 两个最深的收获。**第一，崩溃恢复要区分两种损坏**：恢复时读到一半 EOF 是撕裂写——说明崩溃发生在追加过程中，这条写'从未发生'，在断点处 truncate 就行；但帧完整、CRC 对不上，是 bit rot 静默损坏——这时**必须拒绝启动**，因为跳过它等于静默销毁一条已提交的数据，和丢弃一条未完成的写是完全不同的语义。这两种情况我用两个不同的错误值区分：`io.ErrUnexpectedEOF` 和 `errGarbageLength` 算尾部撕裂，`ErrCorrupt` 是致命的。
>
> **第二，持久性的价格**。我做了基准：不 fsync 顺序写约 3 微秒一次；每次写都 fsync 是 **4 毫秒一次，慢三个数量级**。这个数字是理解一整类系统设计的钥匙：为什么数据库要组提交、为什么异步复制会丢数据、为什么 Kafka 攒批——全都是在摊薄这 4 毫秒。"

## 可主动抛出的数字

- 覆盖写 1000 次：逻辑 256000B → 落盘 272000B，**1.06x**
- 顺序写不 fsync **~3µs/op**；每次 fsync **~4ms/op**（差 1000 倍）
- 随机点查 **~1.6µs/op**
- 恢复：750 条记录重放，tombstone 的 key 不复活

## 追问链

**Q1：删除为什么要写墓碑，不能直接把 KeyDir 里的条目删了？**
> "KeyDir 只是缓存。直接删内存条目，老段里那条记录还在，重启重放日志时它又回来了。所以删除也是一次追加——一条 `Deleted=true` 的记录，让重放逻辑和 merge 逻辑都看见'这个 key 后来被删了'。"

**Q2（追）：merge 之后墓碑能删吗？**
> "能，而且必须删——merge 只抄'存活记录'，墓碑的作用完成后自然消失。条件是 merge 覆盖到包含旧值的所有段，这个实现里 merge 抄写全部存活数据后删掉全部旧段，所以成立。"

**Q3：crc 对不上为什么不能跳过那条记录继续？**
> "跳过 = 无感知丢数据。区分两类错误是我这个项目的核心设计：短读和荒谬长度说明'写没写完'，丢掉它语义正确；帧完整 CRC 错说明'已经确认的数据坏了'，系统没有权力替用户决定丢哪条。所以非最后一段出现损坏直接拒绝启动；最后一段才允许按撕裂写截断。"

**Q4（追）：那如果生产上真遇到拒绝启动怎么办？**
> "这正是设计意图：把静默损坏变成显式故障，交给人（或运维工具）决策。类比：PostgreSQL 页校验失败也是拒绝启动。可加的缓解是冗余副本，而不是'跳过坏记录'。"

**Q5：写放大 1.06x 看起来很优秀，为什么大家不都用它？**
> "因为三个硬限制：KeyDir 必须全内存，key 多了内存爆；哈希序不是键序，**范围扫描做不到**——'查最近十分钟订单'这种需求直接出局；merge 期间我这个实现还阻塞写。所以 bitcask 适合 key 数量可控的点查场景，比如 Riak 的原始场景。要范围扫描就得换 LSM 或 B+ 树——这是我下一个模块做的事。"

**Q6：fsync 4ms，那有没有办法既快又不丢？**
> "有，就是**组提交**：攒 N 条写一次 fsync，把 4ms 摊到 N 条上，持久性保证从'每条'放宽到'这一批'。再往上是复制：多数派 fsync 才算确认，这就是后面 quorum/raft 的思路。我的基准页里专门写了一句：这个 4ms 就是异步复制丢数据的物理根源——大家不是不知道会丢，是丢不起这个延迟。"

**Q7：和 Redis 比，什么时候选谁？**
> "Redis 全内存，重启要么冷启动要么靠 RDB/AOF 恢复，内存贵；bitcask 值在磁盘、只有索引在内存，容量便宜、重启只需重放日志重建 KeyDir。写吞吐两者都高，读延迟 bitcask 多一次磁盘 pread（页缓存命中时也不慢）。海量 key、点查、允许慢启动恢复——bitcask 系。需要集合运算、pub/sub、脚本——Redis。"

## 对照真实系统（被问"和 Riak bitcask 差在哪"）

| 我的教学版 | 生产 Bitcask（Riak） |
|---|---|
| merge 阻塞写 | 在线 merge（读写都不停） |
| 启动重放全日志 | **hint 文件**（只有 key→位置的迷你段，启动快得多） |
| 单目录 | 多目录挂多盘、并发 merge |
| fd 缓存 LRU 64 | 可配 fd 上限 + 动态调整 |

主动说："生产版最关键的优化是 hint 文件——把'重放全量数据'变成'重放索引'，启动从分钟级到秒级。"

## 主动承认的边界

- merge 阻塞写入（真实是在线合并）；
- 无 hint 文件，启动慢（恢复时间 ∝ 日志长度）；
- KeyDir 无磁盘溢出方案；
- 没有并发写入的锁优化（单写锁）。

一句话收尾："这些简化是故意的——这个模块的目标是把'追加日志 + 内存索引'的本质和代价讲到最清楚，Riak 的论文和源码是下一步对照的路径。"
