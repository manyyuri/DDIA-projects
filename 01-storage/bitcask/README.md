# bitcask — 追加日志 + 内存哈希表

> DDIA §3.1 "Hash Indexes"。最简单的能用存储引擎，也是把"日志是真相、索引是缓存"讲得最清楚的一个。

## 机制

```
写入：  追加一条记录到段文件 → 更新内存哈希表 KeyDir[key] = (fileID, offset, size)
读取：  查 KeyDir → 一次 pread 拿到值        ← O(1)，没有读放大
删除：  追加一条墓碑记录（不是删除旧记录）
空间回收：Merge —— 把存活记录重写到新段，删掉旧段
崩溃恢复：从文件头顺序扫描，重建 KeyDir
```

记录格式（小端）：

```
+-------+------+--------+--------+-----+-------+
| crc32 | type | keyLen | valLen | key | value |
| 4B    | 1B   | 4B     | 4B     |     |       |
+-------+------+--------+--------+-----+-------+
```

`crc32` 覆盖校验字段之后的全部内容。

## 关键设计点

### 1. 崩溃恢复要区分两种损坏

这是实现里最值得看的一处。CRC 失败有两种成因，处理方式完全相反：

| 现象 | 成因 | 处理 |
|---|---|---|
| 记录读到一半就 EOF（**短读**） | 追加过程中崩溃 = 撕裂写 | 在断点处 `Truncate`，那条写"从未发生" |
| 帧完整但 CRC 对不上 | **静默损坏**（bit rot、坏盘） | **拒绝启动**，因为丢弃它等于静默销毁已提交数据 |
| 长度前缀不可信（> 上限） | 页刷了一半留下的垃圾 | 按撕裂写处理，截断 |

区分靠 `record.go` 里两个不同的错误值：`io.ErrUnexpectedEOF`（短读）vs `errGarbageLength`（长度荒谬）都算尾部撕裂；只有 `ErrCorrupt`（帧完整 + 校验错）是致命的。

如果损坏发生在**非最后一个段**（已经封存的历史文件），那就不是"尾部的写没完成"，而是真的数据丢失 —— `Open` 直接报错。

### 2. Merge 是可中断、可重入的

Merge 把存活记录写进一个 **id 最大的新段**，然后删旧段。因为恢复时按 id 顺序重放、同 key 后者胜，所以：

- 合并写了一半就崩溃 → 已写进新段的 key 生效，没写到的仍然解析到旧段 → **结果依然正确**；
- 合并是幂等的，重跑一次没有副作用。

`TestMergeIsCrashSafe` 手工构造了这个中间态来验证。

### 3. fsync 策略是显式的

`SyncOnWrite` 关闭（默认）时进程崩溃不丢数据（日志自洽），但**断电会丢最后几条写**。打开后每次写都 `fsync`，吞吐掉两个数量级。这是"持久性 vs 吞吐"最直白的一次呈现。

## 代码地图

| 文件 | 内容 |
|---|---|
| `record.go` | 记录编解码、CRC、两类损坏的区分 |
| `segment.go` | 段文件、id 解析、**fd 缓存（LRU）**（合并几千个段时不会打爆 fd 上限） |
| `keydir.go`（在 `db.go` 里） | 内存哈希索引 + RWMutex |
| `db.go` | Open/恢复、Put/Get/Delete、段轮转、Close |
| `merge.go` | 空间回收 |

## 实验

```bash
go test ./01-storage/bitcask/ -v -count=1        # 8 个测试
go test ./01-storage/bitcask/ -run '^$' -bench . # 基准
```

**实测数据：**

| 实验 | 结果 | 说明 |
|---|---|---|
| `TestWriteAmplificationIsVisible` | 逻辑写 256000B → 落盘 272000B，**1.06x** | 覆盖写同一个 key 1000 次就是落盘 1000 条完整记录 |
| `TestPersistenceAcrossReopen` | 重放 750 条记录 | 500 次 put + 250 次 tombstone，删掉的 key 不会复活 |
| `TestTornWriteRecovery` | 10 条完好记录全部保留 | 撕裂的第 11 条被精确丢弃 |
| `TestSegmentRotationAndMergeReclaimsSpace` | 4000 条记录 → 合并后不足一半 | 20 个存活 key |

**基准（`make bench`，M1 Pro，16B key / 256B value）：**

| 场景 | 延迟 | 吞吐 |
|---|---|---|
| 顺序写（不 fsync） | **~3 µs/op** | 70–85 MB/s |
| 随机点查 | **~1.6 µs/op** | ~160 MB/s |
| 顺序写（每次 `fsync`） | **~4 ms/op** | 0.06 MB/s |

（数字随机器波动，量级是稳定的：**一次 fsync 要 4 毫秒左右，比不 fsync 慢三个数量级**。） 这个数字是理解"为什么所有数据库都要批量提交/组提交（group commit）"的起点：一次 fsync 能刷多少条写、就把多少次 4.3ms 摊掉。也是理解"异步复制丢数据"的物理基础——fsync 的成本太高，所以大家才会为了延迟去放宽持久性。

## 取舍

| 得到 | 代价 |
|---|---|
| 点查 O(1)，无读放大 | **KeyDir 必须全部放进内存**（键 + 8B×3 元数据） |
| 追加写极快，天然崩溃安全 | **没有范围扫描**——哈希顺序不是键顺序 |
| 无写放大（1x） | 更新即重写，**空间 + 写放大随更新次数线性增长** |
| 恢复简单 | 恢复时间 ∝ 日志总长（没有检查点/hint 文件） |

**什么时候选它**：key 数量可控、访问模式是点查、写入量远大于数据增长（比如缓存、会话、消息去重表）。

## 自测题

1. 为什么删除必须写墓碑，而不能直接从 KeyDir 里删掉条目？（提示：老段里还有旧值）
2. Merge 把新段 id 设成最大值，为什么这样就"可中断"？换成最小值会怎样？
3. `VerifyOnRead` 默认关闭。不打开它会引入哪种故障？（提示：磁盘 bit rot 之后，你什么时候才会发现）
4. 这个引擎没法做 `range scan`。如果业务需要"查最近 10 分钟的所有订单"，你要怎么改？（提示：排序结构、二级索引、或者干脆换引擎）

## 已知边界

- Merge 期间**阻塞写入**（真实 Bitcask 在线合并 + 写 hint 文件加速启动）。
- KeyDir 全内存，没有溢出到磁盘的方案。
- 没有 hint 文件，启动时要重放整个日志。
- fd 缓存大小默认 64，超大集群需要调。
