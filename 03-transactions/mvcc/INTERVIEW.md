# INTERVIEW — mvcc 讲解

## 30 秒定位

> "多版本并发控制的实现，重点不是'多版本'本身，而是**快照隔离到底防住了什么、防不住什么**。我复现了写偏斜：两个医生的值班事务在快照隔离下都提交成功，'至少一人在岗'的不变量被破坏，而且没有任何报错。然后加了 OCC 式读集校验把它挡住。这个'先看到 bug 再看修复'的对照测试是整个模块的核心。"

## 两分钟讲解稿

> "机制：每个 key 是一条版本链，版本带 `[startTS, endTS)` 生命周期。读的可见性判定就一行：`startTS <= 我的快照 && (endTS == 0 || endTS > 我的快照)`。写不覆盖任何东西——追加新版本，把前一个版本的 endTS 改成我的提交时间。这样**读不阻塞写、写不阻塞读**是免费得到的：读者看历史版本，写者只追加。可重复读也是免费的：事务的 readTS 在开始时就固定了。
>
> 提交时做首提交者胜（first-committer-wins）：检查我的写集里每个 key 有没有在我快照之后被人改过，有就冲突拒绝。这挡住了**丢失更新**——两个事务同时读 counter=1 各自加一、各自写回，后提交的被拒，`TestLostUpdateIsPrevented` 里最终是 2 不是 3。
>
> 但这只检查写集。**写偏斜**钻的是读集的洞：两个事务读同一批数据（'两人都在岗'）、写不同的行（各自下线），写集不相交 → 冲突检测全部放行 → 两个都提交 → 在岗 0 人。我的测试故意断言'两个都提交成功'，先让你看到这个静默 bug，再用 Serializable 模式的读集校验修好：提交时检查**读集里的 key** 是否被人改过，第二个事务被拒、重试后读到只剩一人、自己拒绝下线。不变量保住了。
>
> 第三个关键点是 GC：历史版本只能删到'最老活跃快照'为止。我的测试里一个长事务占着旧快照，中间插入 5 个新版本，GC 必须返回 0——一个都不能删。**长事务是 MVCC 的天敌**，这就是 PostgreSQL 要有 idle_in_transaction_session_timeout 的原因。"

## 可主动抛出的数字 / 断言

- `TestWriteSkewIsAllowedUnderSnapshotIsolation`：断言 bug 存在（两事务都提交、不变量破坏、零报错）
- `TestWriteSkewIsPreventedBySerializable`：加读集校验后第二个被拒
- `TestGarbageCollectionRespectsOpenSnapshots`：长事务钉住快照，GC 返回 0；结束后收回 5 个版本

## 追问链

**Q1：丢失更新和写偏斜的区别，一句话说清。**
> "冲突发生在哪一层：丢失更新是**两个事务写同一个 key**（写-写冲突），首提交者胜能挡；写偏斜是**两个事务读同一批 key、写不同的 key**（读-写冲突），写集不相交所以写集检测看不见它。写偏斜的本质是：不变量依赖于'我读到的状态在提交时仍然成立'，而快照隔离不维护这个承诺。"

**Q2（追）：除了值班场景，还有什么真实写偏斜的例子？**
> "黑白名单互斥（'两人不能同时在彼此黑名单'）、唯一用户名检查（两个事务都查'没人用过这个名'、然后各自插入——不过这个在唯一索引下会被 DB 挡住）、余额与额度双重检查的取款。共同模式：**先读后判定、判定的前提跨多行**。"

**Q3：MySQL 的可重复读有写偏斜吗？**
> "实践上很难发生，但原因不是没有写偏斜的语义空间，而是 InnoDB 的 RR 加了两层非标准的东西：① 一致性读之外，DML 用**当前读**（读到最新已提交版本再改）；② 间隙锁把范围锁住。这两个把大多数写偏斜场景'顺便'挡了，代价是死锁率上升和幻读语义的微妙。PostgreSQL 的 SI 是标准快照隔离，写偏斜是真的存在的，官方文档专门有'Serialization Anomaly'一节。所以我的回答是：**写偏斜是否存在取决于具体实现的隔离实现细节，而不是隔离级别的名字**——名字相同的级别在不同数据库里行为不同，这是我在这个模块里最大的收获之一。"

**Q4（追）：那你的实现为什么不用 MySQL 那套，用 OCC？**
> "我的目标是教学上最容易解释对的版本：OCC 读集校验三行代码就把可串行化的核心矛盾摆出来了——'读的时候看到的世界，提交时还作数吗'。代价是保守：只要读集被任何人碰过就杀，误杀率高。PostgreSQL 的 SSI 更聪明：它追踪读写依赖图，检测'危险结构'（rw 反依赖成环）才杀，能放过大量实际安全的事务。我的 README 里明确写了'比 SSI 保守，更容易误杀'。"

**Q5：读集校验为什么能挡写偏斜？原理上它把隔离级别提到了哪？**
> "它等价于可串行化的一个充分条件：每个事务提交时验证'我的读世界仍是最新世界'。写偏斜依赖的恰恰是'我读的时候别人还没改'，读集校验把这句话变成提交时的硬检查。理论框架是 Cornad 等人的 Serializable Snapshot Isolation：只杀'处在危险结构里'的事务就能保证可串行化。我的版本是它的超集（杀得更多），安全性不弱于它，吞吐更差。"

**Q6：MVCC 里的长事务到底有多可怕？**
> "量化一下：每秒 1 万写、事务跑 2 小时，这个快照之后累积 7200 万个不可回收的版本——表膨胀、索引膨胀、扫描全变慢， PostgreSQL 里这叫 bloat，vacuum 追不上。所以生产系统的三件套：空闲事务超时强杀、监控最老事务年龄、把长分析查询打到只读副本（牺牲一点新鲜度换主库的 GC 自由）。我的测试是把 5 个版本全钉死，规模小但机制相同。"

**Q7（追）：只读副本能完全躲开吗？**
> "躲开的是主库的版本链压力（副本也有自己的快照约束，但逻辑复制是已提交行流，没有主库那么重的多版本堆积）。真正要小心的是副本上的长查询会延迟复制应用（物理复制下副本也要为读快照保留 WAL）。没有银弹，只有把成本挪到愿意付的地方。"

**Q8：删除在 MVCC 里是什么？**
> "一条 `deleted=true` 的版本，不是摘链。否则旧快照读这个 key 会得到'不存在'，但正确的快照语义是'它当时存在、值是 v1'。删除也要走版本链，和 LSM 墓碑、leaderless 墓碑是同一个思想：**修改/删除一个多版本、多副本的事实时，操作本身也必须是新版本**。"

## 对照真实系统

- PostgreSQL：SI 是默认（RR），9.1+ 有 SSI（可串行化）；我的 OCC 校验 = SSI 的保守版；
- MySQL InnoDB：RR + 当前读 + 间隙锁，另一个方向解同一道题；
- Oracle/SQL Server：undo 段式 MVCC，读旧版本靠回滚段而不是版本链，长事务会撑爆 undo——同一个天敌。

## 主动承认的边界

- 全内存、无 WAL、无索引（Scan 全表）；
- 无锁、无死锁检测（冲突立即失败，重试交给调用方）；
- OCC 比 SSI 保守，误杀多；
- 没有分布式事务（那部分在 twopc 模块）。

一句话收尾："这个模块给我的是对'隔离级别'的祛魅：**隔离级别不是标签，是一组具体机制的后果**。我能把 SI 的每个漏洞和每个补丁都对应到测试编号上。"
